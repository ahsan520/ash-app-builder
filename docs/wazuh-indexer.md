# The central Wazuh indexer (task E6e): what to provision, how to set it up, how ASIX reads it

Status: **ASIX side built 2026-11-01** (registry, read-only client, three routes, the Vulnerabilities tab; see `docs/endpoints.md`, "E6e as built"). **Indexer scripts built 2026-11-01 (E6h):** `scripts/deploy/install-wazuh-indexer.sh` (steps 1 to 2 below) and `scripts/deploy/wazuh-indexer-tenant.sh` (step 3 and the registration file of step 6); see "The two scripts" below. **Not built:** the manager side (E6g: turning vulnerability detection on and pointing the manager at this indexer). **Nothing in this page was run against a real Wazuh indexer**: the scripts were run only with stand-ins for the package manager and for the security API, and the text is written from the Wazuh documentation and from what the stand-in in `tests/fixtures/fake-wazuh-indexer.js` was built to match. Where a step is a guess, it says so. Check each command against the Wazuh 4.14 installation guide before running it.

## Decisions (change them if you disagree)

1. **Why an indexer at all.** From Wazuh 4.8 the manager keeps the vulnerabilities it detects only in the Wazuh indexer, in an index named `wazuh-states-vulnerabilities-<manager name>`. The manager API no longer lists them, and the manager turns detection off without an indexer. So the Vulnerabilities tab needs one.
2. **One central indexer for ASIX, on its own VM. Not on the broker VMs, not a Kubernetes pod.** The broker VM stays small (E4b sizes). The indexer is a Java search engine that wants memory and fast disk, like the central manager (E4c), so it is a VM for the same reasons.
3. **It holds the vulnerability findings and nothing else.** No alerts, no archives: ASIX already stores and searches those. This keeps the disk small and the indexer's job narrow.
4. **One index per manager, one indexer user per tenant that can read only that index.** ASIX stores the exact index name per tenant and never takes it from a request (`src/endpoints/wazuh-indexer-store.js`). The indexer user's role is a second wall behind ASIX's own.
5. **The events of enterprise customers stay in ClickHouse; OpenSearch is not needed for them.** See the last section.

## What to provision

These are **my estimates, not measurements**. Wazuh's published sizing (4 vCPU, 8 GiB, 50 GB for 1 to 25 agents on one host) is for the whole stack with alerts indexed, so it is not this indexer's job, but it is a floor for memory. Look again after the first real client.

| Size | vCPU | Memory | JVM heap | SSD disk | Machines (all tenants together) |
| --- | --- | --- | --- | --- | --- |
| **start here** | **4** | **16 GB** | **8 GB** | **100 GB** | **up to about 500** |
| larger | 8 | 32 GB | 16 GB | 250 GB | up to about 5,000 |
| beyond | 3 nodes, each 8 vCPU / 32 GB | | 16 GB | 250 GB each | one replica per index, so a node can be lost |

- **Disk arithmetic.** A finding is one document of roughly 1.5 to 3 KB. A Linux server often has 50 to 300 findings, a Windows machine more. 5,000 machines x 200 findings x 3 KB is about 3 GB before overhead; with overhead and a replica count of 0 or 1, still far under the table. **Memory (heap) is the limit, not disk.**
- **Heap** is half of the memory, never above about 31 GB. Set it in the indexer's `jvm.options` (`-Xms` and `-Xmx` the same).
- **A single node is not highly available.** The findings can be rebuilt (the manager scans again), so one node is acceptable at the start; a second and third node come with the first client that needs the tab to survive a node loss. (How fast a manager resends its findings after the index is lost has not been tried.)
- **OS and kernel setting.** Ubuntu 22.04 or 24.04 (both are on Wazuh's supported list). Set `vm.max_map_count=262144` (OpenSearch refuses to start in production mode without it) and keep the disk under about 80% full: OpenSearch stops allocating at its low watermark (85%) and blocks writes at the flood-stage watermark (95%).
- **Network.** 9200/tcp from the managers (broker VMs, central managers) and from the ASIX API pods **only**; 9300/tcp between indexer nodes only; never to the internet. The manager also needs outbound HTTPS for the vulnerability feed (Wazuh's own content service; check the host name on the pinned version, and that the client's firewall allows it).

## Set-up, in this order

1. **Create the VM** (table above). Static address or a stable name. Clock in sync (`docs/vm-clock.md`).
2. **Install the indexer: `sudo ./scripts/deploy/install-wazuh-indexer.sh --address <name or address the managers will use>` (E6h; `--check` first), or by hand with Wazuh's installation assistant.** The script does what the rest of this step describes without the assistant (apt package pinned and held, own certificates, one node), see "The two scripts". By hand: The assistant's indexer-only steps are, as I know them for 4.x: write a `config.yml` naming the indexer node, `bash wazuh-install.sh --generate-config-files`, then `bash wazuh-install.sh --wazuh-indexer <node name>`, then `bash wazuh-install.sh --start-cluster` on one node (check the exact options in the 4.14 guide). It makes the certificates (`wazuh-install-files.tar`: a root CA, the node certificate, an admin certificate) and the passwords of the built-in users. **Keep that tar and the password file offline; they are the keys of the indexer.** Pin the package version the way `install-wazuh-manager.sh` pins the manager's (4.14.9).
3. **Create one read-only user and role per tenant: `sudo ./scripts/deploy/wazuh-indexer-tenant.sh --tenant-name "Acme Corp" --manager-name <manager name> --address <indexer address>` (E6h), or by hand** (as the indexer's `admin`, with the security API; the paths are the OpenSearch security plugin's, which Wazuh ships, not tried here):
   ```
   PUT  /_plugins/_security/api/roles/asix_vuln_read_<tenant>
        { "index_permissions": [ { "index_patterns": ["wazuh-states-vulnerabilities-<manager name>"], "allowed_actions": ["read"] } ] }
   PUT  /_plugins/_security/api/internalusers/asix-vuln-<tenant>      { "password": "<long random>" }
   PUT  /_plugins/_security/api/rolesmapping/asix_vuln_read_<tenant>  { "users": ["asix-vuln-<tenant>"] }
   ```
   ASIX only ever asks for a count and a search on that one index, so `read` on that exact name is enough. **Do not use `admin` for ASIX.**
4. **Point the manager at the indexer (E6g, by hand until it is built).** From the Wazuh documentation for 4.8 and later, in the manager's `ossec.conf`: `<vulnerability-detection>` with `<enabled>yes</enabled>` and `<index-status>yes</index-status>`, and an `<indexer>` block with `<enabled>yes</enabled>`, the indexer's `<hosts>`, and `<ssl>` pointing at the root CA and a client certificate and key; the indexer user name and password go into the manager's keystore (`/var/ossec/bin/wazuh-keystore`), not into `ossec.conf`. The manager's writer user needs more than read: give it its own role on its own index pattern with write and index-creation rights, and widen it if `ossec.log` reports a refused action (I do not know the exact action list the connector needs). **Re-running `install-wazuh-manager.sh` switches detection off again** (E4b does that on purpose); E6g will make it a choice.
5. **Wait for the first scan.** The manager downloads the feed, then scans each machine's installed software. Check on the indexer: `GET /_cat/indices/wazuh-states-vulnerabilities-*?v` (as admin). The name you see is the index to register.
6. **Register it in ASIX** (an operator, from where `kubectl` works). `ca_pem` is the indexer's **root CA** (`root-ca.pem`), exactly one certificate:
   ```
   {"url":"https://wazuh-indexer.internal:9200","user":"asix-vuln-acme","password":"...","ca_pem":"-----BEGIN CERTIFICATE-----...","index":"wazuh-states-vulnerabilities-<manager name>","label":"Acme"}
   kubectl -n asix-platform exec -i deploy/asix-api -- node src/endpoints/wazuh-indexer-cli.js register --tenant "Acme Corp" < indexer-registration.json
   kubectl -n asix-platform exec    deploy/asix-api -- node src/endpoints/wazuh-indexer-cli.js check    --tenant "Acme Corp"
   ```
   `register` reads the index first and saves only if that works; use `--no-check` when the index does not exist yet. Then open Endpoints, **Vulnerabilities**.
7. **Change a password or replace the certificates:** run `register` again (it replaces the row). A replaced indexer certificate shows in the tab as `TLS: the indexer's certificate is not the one registered` until you do.

## What ASIX reads, and what it never does

Two calls only: `GET /<index>/_count` and `POST /<index>/_search` with a body ASIX builds from a short list of validated filters (severity, machine id, vulnerability id, text; sort; 100 rows at most). It never sends a body, an index name or a path from a request, never writes, follows no redirects, and trusts only the registered certificate. The answer is cut down to a fixed list of fields. The field names it reads are the documented ones for 4.8 and later (`agent.id`, `agent.name`, `package.name`, `package.version`, `vulnerability.id`, `vulnerability.severity`, `vulnerability.score.base`, `vulnerability.detected_at` and a few more). **Checked against a real 4.14.9 index on 2026-11-01** (one document, Ubuntu agent): every field name below matched. Two shapes to know: `vulnerability.reference` is ONE string with the links joined by `, ` (ASIX splits it), and a finding the scanner has not scored yet has `severity: "-"`, `score.base: -1.0` and `under_evaluation: true` (shown as severity unknown, no score). **If the real index spells one differently, that column shows a dash and the filter on it finds nothing**: that is the first thing to look at on the first real run (`GET /<index>/_search?size=1` as admin shows a real document).

## Events: is OpenSearch needed for fast search? (answer for enterprise customers)

**No: ClickHouse is enough for ASIX's own events, and OpenSearch is only here because Wazuh insists on it for findings.** ASIX searches are time-bounded and tenant-bounded, and the table is already laid out for that: `src/events/clickhouse-store.js` sorts it by `(tenant_id, received_at, id)`, so a search over a recent window reads a small slice. Counts, group-bys and top-N (what a SIEM does all day) are where ClickHouse is much faster and far cheaper per GB than a search engine. Where a search engine is better is **free-text search across every field of a large, unstructured log**. The table has **no text index today** (I looked: only the sort key), so a search for a word inside the raw message scans the window. If that becomes slow, the fix is in the table design, not a second system: keep parsed fields as real columns so the common searches never touch the raw text, and add a token or n-gram skip index on the raw message column. If the first enterprise customer's real searches turn out to be mostly free text over many months of raw logs and are still slow after that, measure it then; adding OpenSearch for events would mean a second copy of the data, a second store to secure per tenant, and a second thing to patch.

## The two scripts (E6h, built 2026-11-01)

**`scripts/deploy/install-wazuh-indexer.sh`** (root, Debian or Ubuntu, one node). `--check` looks and changes nothing. Then, each step safe to repeat: the Wazuh apt repository and key (fingerprint printed, `--key-fingerprint` pins it), `wazuh-indexer=4.14.9-1` installed and **held** (the same version as the manager; a different installed version needs `--upgrade`), `vm.max_map_count=262144` (`/etc/sysctl.d/99-asix-indexer.conf`), the heap (a file in `jvm.options.d`: half of the memory, 31 GB at most, or `--heap-gb`; in `--lab` a quarter, 8 GB at most), **certificates made once and never overwritten** (a root CA, a node certificate that names `--address`, the host name, `localhost` and `127.0.0.1`, and an admin certificate; **the CA's private key is not kept**, so adding a node later means a new CA), `opensearch.yml` (one node, all addresses, those certificates; the original is kept as `opensearch.yml.before-asix`), a **random admin password** in `/etc/wazuh-indexer/asix-admin.pass` (root only) hashed into `internal_users.yml` with the security plugin's own `hash.sh` (**the one place a password is on a command line: `hash.sh` takes it only as `-p`, so run this on a machine only administrators can sign in to**), the security configuration loaded (`indexer-security-init.sh`), and the indexer started and asked for `/_cluster/health` as admin (green or yellow, or it stops with the last answer). Minimums: 4 vCPU, 12 GB, 20 GB free (`--lab`: 2 vCPU, 6 GB); below them it stops before changing anything unless `--force`. It does not open the firewall.

**`scripts/deploy/wazuh-indexer-tenant.sh`** (root, on the indexer machine, once per manager). Signs in as admin (password read from the file, given to curl on a file descriptor, never on a command line), then makes the role `asix_vuln_read_<slug>` (**`read` on the one index `wazuh-states-vulnerabilities-<manager name>`, no cluster permission**), the user `asix-vuln-<slug>` with a random password (kept in `/etc/wazuh-indexer/asix-vuln-<slug>.pass`; the same one is reused on a re-run unless `--rotate`) and the mapping. It then **reads the role and the mapping back and refuses to write anything for ASIX unless the role is exactly that one index with `read` and nothing else and only that user has it**. Last it writes `asix-indexer-registration-<slug>.json` (mode 600: url, user, password, root CA, index, label) for `wazuh-indexer-cli.js register` (use `--no-check` until the manager has made the index). The manager name must be lower case (ASIX's table accepts nothing else). `--check` says whether the role and user exist and writes nothing.

**Checked** (`tests/wazuh-indexer-scripts.test.js`, 25 tests): the real scripts with the real openssl, python3 and curl. The installer with stand-ins for apt, dpkg, gpg, systemctl, ss, sysctl and the security plugin's tools: the checks and their `--force`, the pinned and held package, the key fingerprint, the certificates (the node certificate verifies against the root CA and names the address, the host name and 127.0.0.1; the admin one verifies too; no CA key kept), `opensearch.yml`, the admin hash written into the users file with the other users untouched, the heap rules, a second run changing nothing, and every stop (no listening port, failed security initialisation, a red cluster, a bad hash, no admin entry, no hasher). The tenant script against a stand-in security API over HTTPS: the role, user and mapping, the read-back catching a role with extra rights or a wrong mapping, the same password on a re-run, `--rotate`, two managers with separate roles, a wrong admin password, an unreachable indexer or the wrong CA, and no password in the output or on any curl command line. The registration file is accepted by the real `parseRegistration`. **NOT checked: a real indexer.** Likely differences, in the order they would bite: the layout of the package (`/usr/share/wazuh-indexer/plugins/opensearch-security/tools/hash.sh`, `bin/indexer-security-init.sh`, `opensearch-security/internal_users.yml`, the `jvm.options.d` folder), the keys of `opensearch.yml` (`discovery.type: single-node`, the `plugins.security.*` names and `compatibility.override_main_response_version`), whether the admin certificate alone may call the security API, the answer words of the security API (the script accepts HTTP 200 or 201 and reads the role back), and whether the manager (E6g) can write with the credentials it is given. The script stops with a message in each case rather than going on.

## Watching the indexer's disk (E6i, built 2026-11-01)

The indexer makes its indices read-only at 95% disk, and the Vulnerabilities tab then goes stale. `scripts/deploy/install-indexer-health.sh` (root, on the indexer machine) installs `asix-indexer-health.sh` with a systemd timer (every 5 minutes, `--interval-min`, keep it at 7 or less) that reports the disk and the indexer's health to ASIX; ASIX raises four alerts.

1. In ASIX, Settings, Installers: make an ingestion key named for the machine (for example `indexer-vm`) and save it to a file on the indexer VM.
2. `sudo ./scripts/deploy/install-indexer-health.sh --url https://ASIX-ADDRESS:30443 --key-file KEYFILE --ca-file ASIX-CERT --check` shows what would be sent and changes nothing; run again without `--check` to install. A self-signed ASIX needs `--ca-file`. The first report is sent at the end, so a wrong address or key shows now.
3. Collectors page: press **Alert if silent** on `indexer-<host>` (for example 20 minutes) to be told when the reports stop. Search dataset `indexer-health` shows each report.
4. `--remove` undoes it. Settings are in `/etc/asix-indexer/health.env`, the key in `health.key` (root only); the admin password in `/etc/wazuh-indexer/asix-admin.pass` is read for two GET calls and never printed or put on a command line.

**Alerts** (Detections page, on by default, grouped by host): disk filling 80% to under 90% (medium); disk nearly full 90% and over (high); refusing writes, any index read-only (critical); unhealthy, red or unreachable twice in 15 minutes (high). **To free space** when it fires: purge old kernels on the agents (their findings leave the index), remove indices of managers that no longer exist, or grow the disk; after freeing space lift the block with `PUT /_all/_settings {"index.blocks.read_only_allow_delete": null}` as admin (OpenSearch lifts it itself below the high watermark in current versions, check). **Not verified** against a real indexer VM yet; the data path is `/var/lib/wazuh-indexer` (`--data-path`). Tests: `tests/indexer-health-rules.test.js`, `tests/indexer-health-script.test.js`.

## Lab: the broker VM as the indexer

**Possible for the lab, not for production** (decision 2 above stands: the broker VM stays small and is the client's, and a second Java service on it competes with the Wazuh manager for memory). To try the tab with the one VM that already runs the Wazuh manager (E4b):
1. **Give the VM more.** The E4b size (4 vCPU, 8 GB) is not enough for both; use **8 vCPU, 16 GB and 150 GB SSD** (my estimate). The memory is the limit: the indexer's heap is 4 GB with `--lab`, the manager, Vector and the system need the rest.
2. Run `sudo ./scripts/deploy/install-wazuh-indexer.sh --lab --address <the VM's address>`. The manager's ports (1514, 1515, 55000) and the indexer's (9200, 9300) do not clash.
3. Run `wazuh-indexer-tenant.sh` for the lab tenant with the manager's name (`ls /var/ossec/etc/` or the name in the manager's `ossec.conf`; the indexer shows the real index name after the first scan: `GET /_cat/indices/wazuh-states-vulnerabilities-*?v`).
4. Point the manager at `https://127.0.0.1:9200` (E6g by hand, step 4 above): on the same machine the manager's indexer address is loopback and the certificate names 127.0.0.1. Register the file from step 3 with the VM's **real** address in `--address` (ASIX must not be given a loopback address).
5. Firewall: 9200/tcp from the ASIX node only (and the manager reaches it over loopback). Re-running `install-wazuh-manager.sh` switches vulnerability detection off again.
If the lab VM runs short of memory the first sign is the manager or the indexer being killed (`dmesg | grep -i oom`); raise the VM or lower `--heap-gb` and re-run. **For production the plan is unchanged: ASIX, the brokers with their managers, and a dedicated indexer as separate VMs.**
