# Broker capacity, groups and placement (task E9)

Status: **built 2026-10-31**. Real PostgreSQL 16 (schema applied twice), unit, portal and script tests; **not yet run on the k3s box or on broker-1, not seen in a browser, and the new heartbeat script has never run on a real broker VM.** Read the "Estimate" section before trusting any number on the page.

## What was asked, and what this is

Clients have 1,000 to 3,000 endpoints (the largest about 10,000). Each broker VM that runs an endpoint manager (`docs/endpoints.md`, E4b) can look after only so many agents, and that depends on the VM's CPUs and memory. The request: ASIX should decide how many agents report to each broker from its CPU and memory, and brokers should form a group so that a mid-size or large client can be spread over several brokers.

**"ASIX has write access to the broker" is read as: ASIX decides, and the broker is told through the mechanism that already exists.** The broker config pull (`docs/broker-vm.md`, "Config from ASIX") is ASIX writing settings to a broker: the broker asks, checks the signature, applies, and puts the old settings back if anything fails. E9 adds **no new way to write to a broker** (no inbound SSH or agent), because it does not need one: the limit is applied where the choice is made, which is when ASIX picks the address that goes into an agent installer. If you meant ASIX logging in to broker VMs to change things, that is a different and riskier design and it is not built; say so before it is.

## What it does

1. **The broker says what it is.** `deploy/broker/asix-broker-heartbeat.sh` adds two things to the heartbeat it already sends every minute: `collector.host` (`cpus`, `mem_mb`, from `nproc` and `/proc/meminfo`) and `collector.agents` (the number of enrolled agents: lines in the manager's `/var/ossec/etc/client.keys`). A broker with no manager, or one that cannot read the file, sends no count. Stored in new columns on `collectors` (`host_cpus`, `host_mem_mb`, `agents_enrolled`); a heartbeat without them leaves the stored values alone.
2. **A limit per broker.** Recommended = the smaller of `CPUs x 12` and `GB of memory x 6` (4 CPUs and 8 GB give 45 to 48). You can set your own number per broker (`agent_limit`); empty uses the estimate.
3. **A state per broker and per group:** Room, Nearly full (80% of the limit or more), Full (at or over the limit), Unknown (no limit, or no agent count).
4. **Groups.** A group is a name you give to brokers that serve the same client (`broker_group`). The page shows each group's agents against its total limit and **which broker the next machine goes to: the connected broker with a manager that is least full in proportion to its own limit** (so a bigger VM takes more machines than a smaller one), ties to the most free slots, then the name.
5. **Planning.** "How many brokers does a client need?": machines divided by the typical broker's limit (the median of the connected brokers that know theirs), rounded up, **plus one spare** so a broker can be down or upgrading.
6. **An installer pointed at a broker.** `GET /v1/brokers/placement/installer/linux|windows?broker=<id>` or `?broker=auto&broker_group=<name>` makes the same script as Add a machine, with that broker's address. A full broker is refused (409 `BROKER_FULL`) unless `&force=1`; a broker that is not connected, has no manager, or has not said how big it is or how many agents it has is refused (`BROKER_NOT_AVAILABLE`); `auto` with nothing able to take a machine says why for each broker.

## Where it is

- Portal: **Settings, Brokers**. A column **Agents** (`10 / 48 (21%)`, the group beside it, the size and where the limit came from in the tooltip), a **Capacity** button on each row (group and agent limit), and a card **Agent capacity and placement** (groups, next broker, the planner).
- API: `GET /v1/brokers/placement[?endpoints=N]` (`collectors:read`), `PUT /v1/brokers/:id/placement` with `{ "group": "acme", "agent_limit": 60 }` (`collectors:write`; `null` clears one; a key not sent is left alone; a refused request changes nothing), `GET /v1/brokers/placement/installer/:platform` (`capacity:read`). `GET /v1/brokers` also carries `group` and `capacity` per broker and `agents_enrolled`, `capacity_near`, `capacity_full` in the summary. No new permission or role.
- Code: `src/brokers/placement.js` (pure rules), `src/gateway/routes/broker-placement.js` (new), `src/brokers/broker-view.js`, `src/gateway/routes/brokers.js`, `src/ingest/heartbeat.js`, `src/portal/index.html` (banner "Broker capacity and placement"), `deploy/broker/asix-broker-heartbeat.sh`, `k8s/12-schema-init.yaml` (five columns on `collectors`).
- Environment of the API (optional): `ASIX_BROKER_AGENTS_PER_CPU` (default 12) and `ASIX_BROKER_AGENTS_PER_GB` (default 6), whole numbers 1 to 1000; anything else means the default.

## The estimate is not a measurement, and it is cautious

The two rates restate the E4b sizing table (4 CPUs, 8 GB: about 50 agents and 200 events per second sustained). That table assumed busy Windows **servers**, about 4 events per second per agent. **A fleet of office workstations sends far less per agent, so these defaults will say "full" long before the VM is.** At the defaults a client of 3,000 endpoints needs 63 brokers plus a spare, which is not a plan anyone would follow; the page prints the number it used ("at about 48 per broker") so the assumption is visible.

Also note that the sizing documents disagree with each other: `docs/endpoints.md` E4b gives 8 CPUs and 16 GB for "up to about 150 agents" on a broker VM, while E4c gives 8 CPUs and 16 GB for a central manager for 1,000 to 3,000 endpoints. They describe different event volumes and neither was measured. **Before using the planner for a real client: measure events per second per agent on the lab (Windows 11 host and the Linux machines), then either raise the two rates or set `agent_limit` on each broker.** Until then treat the limit as a guard rail and the planner as an illustration.

## What is not built (and the limits that matter)

- **No hard enforcement.** Nothing stops a machine from enrolling on a full broker if someone uses another installer or address; the limit decides only which address ASIX puts in the installer it makes, and the page shows the state.
- **No moving agents.** An agent stays on the manager it enrolled with. Adding a broker to a group does not rebalance existing agents; it takes the next ones.
- **The Endpoints section reads one manager.** Agents on site managers on broker VMs (E4b) are not listed by the Endpoints page (it reads the manager registered for the tenant, E4c). Their **alerts** still arrive through each broker as before and raise ASIX alerts; only the agent list, the configuration checks per machine and the agent-disconnected alert depend on the registered manager. Listing agents across several managers is not built.
- **No load balancing of syslog or HTTP senders across brokers.** Devices are pointed at one broker each (or at a DNS name or virtual address you provide in front of several; ASIX does not build or check that). Wazuh agents choose a manager once, at enrolment.
- **No Wazuh cluster** (master and workers behind a load balancer) for the largest clients; still the plan in `docs/endpoints.md`, not built.
- **The count is enrolled agents, not active ones.** A line in `client.keys` stays until the agent is removed from the manager; a machine that was retired but not removed still counts.
- **The installer address is where ASIX saw the broker's heartbeat come from.** If devices reach the broker by another address or a name, edit the script (the answer says so). IPv6 is not supported by the installer.
- **No alert** for a full broker or group: it is information on the page, like the other broker columns. Nothing is checked against the client's contract or licence.
- The client.keys path is the standard one; `ASIX_WAZUH_KEYS` lets a test use another file. The `vector` user reads it through the `wazuh` group that `bootstrap-broker.sh --wazuh` adds it to; **not confirmed on a real broker**: if the file is not group-readable the broker simply sends no count and its Agents cell stays a dash.

## Deploy and first try

1. Commit and push, then `./sync-and-deploy.sh` on asix1. The schema job adds the five columns (safe to repeat). Existing brokers show a dash in **Agents** until their heartbeat script is replaced.
2. On broker-1 (and every broker that should report): `git pull`, `chmod +x` the scripts as in `docs/broker-vm.md` step 4, then re-run the bootstrap with `--no-install` and **every flag again** (the re-run reinstalls `asix-broker-heartbeat.sh`). Within a minute Settings, Brokers shows the count for a broker that runs a manager.
3. Check on the broker what it will send: `nproc`, `awk '/^MemTotal:/ {print $2}' /proc/meminfo`, `sudo grep -Ec '^[0-9]+ ' /var/ossec/etc/client.keys` (as the `vector` user, `sudo -u vector grep -Ec '^[0-9]+ ' /var/ossec/etc/client.keys`, to see whether it can read it).
4. Press **Capacity** on broker-1, give it a group (for example `lab`) and see the group card appear with "Next machine goes to broker-1". Set a small limit (for example 2) and see the state change to Full when two agents are enrolled, and `GET /v1/brokers/placement/installer/linux?broker=<id>` answer 409.
5. A second broker in the same group (a new VM, the usual bootstrap with `--wazuh-manager`) shows the proportional choice: with different sizes the bigger one gets the next machine until it is as full as the smaller one.

## Parser workers: turned on for the lab (decision, 2026-10-31)

Decision: **2 workers per API replica**, tried on the lab first, then watch **Settings, Parser pool** for events stored unparsed. `k8s/30-asix-api.yaml` now has `ASIX_PARSER_WORKERS` at `"2"`, the memory limit at 768Mi (request 384Mi) and the CPU limit at 1000m (the workers share it; at 500m they would have been throttled). Rolling updates run three pods at once (`maxSurge`), so the API can use up to about 2.3 GB of the node while an update runs; check the node has it before deploying. To go back: set the value to `"0"` and run `./sync-and-deploy.sh`; nothing else changes. What to watch for a few days: the API log line `[parser] 2 parser worker thread(s), ...` at start, **Settings, Parser pool** counters (per pod) and the unparsed count (last 24 hours), `503 INGEST_BUSY` answers in the broker logs, pod restarts and memory (`k3s kubectl -n asix-platform top pod`). Consider turning on the unparsed-events alert (`docs/parser-workers.md`, "Alert when events are stored unparsed") at the same time. **This has run only in tests (CI runs the ingest test on 2 workers) and never on the k3s box.**
