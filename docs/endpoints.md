# ASIX Endpoint Security: endpoint agents behind ASIX (design and task list)

Status: **planned 2026-10-23; E1 (policy module), E2 (saved per tenant, portal page; confirmed working in the browser 2026-10-23) and E3 (a broker pulls, checks and applies the policy) are built.** Nothing from E4 on is built yet. This page is the one place to read before touching any endpoint task; `docs/parallel-work.md` has the task table and `docs/product-plan.md` the one-paragraph summary.

## What was decided (2026-10-23)

1. **Every endpoint runs one agent, and that agent is Wazuh**, installed by an ASIX installer, for both host security (file integrity, configuration and vulnerability checks, active response) and Windows/Linux event collection. A second event-log agent next to it is not wanted: two collectors on one Security channel double the CPU, duplicate events and give two configs to keep in sync.
2. **Wazuh is behind ASIX, not shown as Wazuh.** The agent installs with ASIX names, the Wazuh manager is a backend service, the Wazuh dashboard is not shipped, and the interface is an **Endpoints** section of the ASIX portal. The product name is **ASIX Endpoint Security** (not "EDR": Wazuh has no kernel-level behavioural prevention, and a client or auditor holding us to the word "EDR" would be a problem; revisit the name only if Sysmon plus active-response playbooks close that gap).
3. **Branded names plus an honest notices page.** Branded service, display and installer names are fine. Hiding Wazuh entirely is not: Wazuh is GPLv2, its copyright and licence notices must stay, customer security reviews and SBOM requests will find the processes anyway, and a modified agent we hand to a client carries a source offer. So the installer and the portal carry a **Third-party notices** page that lists Wazuh and its licence. No Wazuh name or logo is used as ASIX branding, and ASIX never says the code is its own. **Have a lawyer read this before the first client installer ships**; this page is not legal advice.
4. **One Windows filter policy in ASIX, enforced in two places.** Splunk-UF-style allow/deny by event ID (and channel), with an optional regex on a field or on the rendered message, plus removal of the long explanatory text many Windows events end with. The Wazuh agent can filter by event ID (an XPath query in the agent group's `agent.conf`) but has no regex, and its alerts carry the rendered message; so the broker (Vector) always enforces the full policy, and the agent group gets whatever part of it XPath can express, as an optimisation only. The same policy can later compile to a Fluent Bit configuration if an ASIX forwarder is ever needed.
5. **The wall of text is not in the event.** Windows adds it when it renders the message from the provider's message file; the structured EventData is the useful part. The policy therefore offers "remove the rendered message" as well as a regex strip.

## Open decisions (ask before building the tasks that need them)

- **Tenant isolation and manager placement (decided 2026-10-23, from client sizes: most clients 1,000 to 3,000 endpoints, the largest about 10,000).** Wazuh has no native multi-tenancy, and at these sizes a shared manager is not worth its isolation risk. So:
  - **Default: one dedicated single-node manager per tenant** (1,000 to 3,000 endpoints), run centrally (a k3s pod with its own volume, or a VM if the ASIX box lacks the capacity), each reachable on its own address or port. Agents are enrolled with that tenant's registration password and group.
  - **Largest tenants (about 10,000 endpoints): a dedicated Wazuh cluster** (one master and several workers behind a load balancer that agents connect to), on its own VMs, in the ASIX environment or at the client site if the client wants data local or has unreliable links.
  - **Small clients (decided 2026-10-23): their agents connect to a Wazuh manager running on the client's own broker VM** (the "site manager" variant), not to a central one: a small client already has a broker, and nothing has to be exposed centrally. A Wazuh agent never talks to Vector directly; it always talks to a Wazuh manager, and the broker's Vector then reads that manager's `alerts.json` / `archives.json` like any other file input. A manager for a few hundred endpoints should be light enough to share the broker VM (verify on the pinned version and add its needs to the broker VM sizing). A shared central manager with one agent group per tenant stays an option for tiny clients only, later, if ever.
  - **A manager beside the broker is therefore the small-client design, and also the choice for any larger client that needs local collection** (long WAN outages, data residency; the Wazuh agent's event buffer is small by default, verify on the pinned version, so a long outage loses events). The cost is one more service to patch and keep in version step with the agents inside the client's network. Do not stretch one Wazuh cluster across WANs; use independent per-site managers that ASIX manages through the API.
  - **Capacity is the real constraint:** managers need their own cores, memory and fast disk (archives of all events from thousands of endpoints are written to `archives.json` for Vector to read). Size from Wazuh's sizing guidance for the pinned version and from measured event rates; the filter policy (E1) is what keeps these volumes down. The ASIX control plane stays small and the managers move to their own nodes.
  - **The installer takes one parameter, the manager address**, so the tier only decides what it points to: the broker VM (small), a dedicated central manager (mid), or the cluster's load balancer (largest). Moving a client between tiers changes that setting, not the design.
  - **Build order is open: which variant first, the site manager on the broker VM (small clients) or the dedicated central manager (mid clients)?** Both share the same API proxy, alert ingest and parsing pack; they differ in deployment (a broker VM installer step versus a Kubernetes template with address or port allocation). The cluster variant for the largest clients comes after both.
- **Pinned Wazuh version** and the upgrade routine (the manager must be at least as new as its agents).
- **Whether Wazuh keeps its own Windows event rules.** If it does, give it a narrow set (high-value Security IDs and Sysmon) and keep those out of anything else collecting the same events, with ownership per channel and event ID so nothing arrives twice. If ASIX detection owns Windows events, Wazuh's Windows event rules stay quiet; its file integrity, vulnerability and configuration checks are unaffected.

## Architecture

- **Endpoint installer** (E5): the portal generates, per tenant, a Windows script (silent install of a pinned agent package, enrolment with a per-tenant registration password, agent group, branded service names, the filter policy) and a Linux shell script (deb/rpm). Same pattern as the broker installers and keys.
- **Manager** (E4): a backend service; its API is reached only through an ASIX proxy that adds the tenant filter. Alerts and archives go through Vector into the event store as today, with a Wazuh JSON parsing pack mapping `data.win.system` / `data.win.eventdata` into the ASIX fields.
- **Portal** (E6): an Endpoints section (agents with status, version, last seen and group; alerts; file integrity; vulnerabilities; configuration checks; the filter policy; third-party notices).
- **Filter policy** (E1 to E3): E1 is the pure module (rules, validation, evaluation, Vector VRL and Wazuh XPath output). E2 stores it and adds the routes and the portal page. E3 makes a broker apply it (a new kind of broker config next to the syslog port and the pause list: pulled with the broker's own key, validated, applied, health-checked, with a way back).

## E1 as built (2026-10-23)

`src/endpoints/win-filter.js` is a pure module (no I/O, nothing wired into the API or portal yet):

- **Policy shape:** `{ version: 1, default: "keep"|"drop", channels: { <name>: { default } }, rules: [ { id, action: "keep"|"drop", channel?, event_ids?: [4656, "4700-4710"], match?: { field?: "message"|<EventData name>, regex }, note? } ], strip_message: bool, message_strip: [ { channel?, event_ids?, regex } ] }`. Rules are checked in order and the first match wins (so a narrow keep rule placed before a broader drop rule works); no match falls back to the channel default, then the policy default. Channel and field names ignore case. A rule with a regex and no field looks at the rendered message.
- **`validate(policy)`** returns `{ ok, errors, policy }` with the normalised copy (IDs as `[lo, hi]`); limits: 200 rules, 50 strip entries, 300-character regexes, event IDs 0 to 65535.
- **Regex subset:** only syntax that Rust (Vector) and JavaScript read the same way. Rejected, with a message: lookaround, back-references, named groups, inline flags (only `(?: )` groups), `\p \P \k \c \A \z \Z \G`, empty classes `[]` / `[^]`, a `[` or `&& ~~ --` inside a class, a `{` that is not a quantifier, a single quote (write `\x27`) and control characters. Two differences remain and are not detectable: `.` matches `\r` in Rust but not in JavaScript, and `\d \w \s` are Unicode in Rust but ASCII in JavaScript. Use `[^\n]` and explicit classes where it matters. Vector is authoritative; `evaluate()` is for previews and tests.
- **`evaluate(policy, event)`** is the reference behaviour; **`toVrl()` / `toVectorTransform()`** generate a Vector `remap` transform (`drop_on_abort = true`) that must agree with it. The default field paths are a Wazuh Windows event (`data.win.system.channel`, `.eventID`, `.message`, `data.win.eventdata.<name>` with the first letter of each EventData name lower-cased); `paths` changes them. Only the variables a policy uses are defined, so Vector prints no warning.
- **`toXPath(policy, channel)` / `toAgentConf(policy, channels)`** give the Wazuh agent group's `<localfile>` blocks. Only a channel whose rules are all event-ID rules with one action, opposite to the channel's default, gets a `<query>` (an exclusion list or an inclusion list); everything else returns the reason and stays at the broker. The broker enforces the whole policy anyway.
- **`presetNoisySecurity()`** is a suggested starting point only (drop Security 4656, 4658, 4690, 5145, 5156, 5158 and strip the message); it is never applied by itself.
- **Checked:** `tests/win-filter.test.js` (17 tests): validation, the reference evaluation, the XPath and `agent.conf` output, and, with a real Vector binary (`VECTOR_BIN`, or `vector` on PATH; run with Vector 0.59.0), `vector validate` and `vector test` on 14 events, including event IDs as text as Wazuh writes them, show the generated transform keeps, drops and strips exactly what `evaluate()` says, with no VRL warnings; six deliberate breaks each make it fail. Without Vector those tests are skipped. **Not checked: the XPath query length limit Wazuh accepts (1024 characters is a cautious guess to verify on the pinned Wazuh version), that a Wazuh agent accepts the generated `<query>` on a real Windows machine, the Wazuh archive field names on the pinned version.** CI has no Vector, so those Vector tests are not part of CI today.
- **Not built (E2, E3):** storing the policy per tenant, routes, permission, the portal page, and the broker pulling and applying it (a broker script change).

## E2 as built (2026-10-23)

The policy is saved per tenant and edited in the portal; **nothing is sent to a broker or an agent yet (that is E3)**.

- **Table `win_filter_policy`** (in `k8s/12-schema-init.yaml`, created by the normal schema job, idempotent): one row per tenant with the policy as JSONB, a `revision` that goes up by one on every save, `updated_at`, `updated_by`; row security by tenant like the other settings tables. No row means no policy: every event is kept, as before.
- **Routes** (`src/gateway/routes/win-filter.js`, registered in `src/gateway/index.js`; store and request rules in `src/endpoints/win-filter-store.js`): `GET /v1/endpoints/win-filter` (the saved policy, revision, the suggested starting point and the limits; a missing table answers with `available: false` instead of failing), `PUT /v1/endpoints/win-filter` with `{ policy, if_revision? }` or `{ clear: true }`, and `POST /v1/endpoints/win-filter/preview` with `{ policy, events? }` (checks a policy against up to 50 sample events and returns the Vector transform, the Wazuh agent group blocks and per-channel XPath or the reason there is none; touches no database).
- **Permissions, no role changes:** read and preview use `capacity:read`, save and remove use `parsing:rules:write`, the same as the Parser pool alert setting. If the filter should get its own permission later, that is a role change to plan separately.
- **Saving is safe against two people editing:** the save reads the row under lock; if `if_revision` is given and is not the current revision (0 = none saved yet) it is refused with 409 and nothing is written. The portal always sends the revision it opened.
- **Portal:** Settings, Data collection, **Windows event filter** (tied to the ingestion module): a JSON editor for the policy, **Check with the sample events** (shows what each sample would do, the agent blocks and the Vector transform), **Save**, **Load the suggested starting point** (the noisy Security IDs preset, never applied by itself) and **Remove the policy**. A JSON editor is the first version; a form for rules is later work.
- **Checked:** `tests/win-filter-store.test.js` (17 tests: request rules, sample events, view, preview, the three routes with permissions, 400/409/503/500 paths), `tests/portal-win-filter.test.js` (10 tests; four deliberate breaks fail it), and against a real Postgres 16 `tests/win-filter-db.test.js` (`ASIX_TEST_DB=1`): schema applied twice with no error, save/read/clear, tenant separation, row security as a non-superuser role (fails when row security is switched off), a stale revision refused with the row untouched, two saves forced to overlap (exactly one wins; fails when the row lock is removed), the revision check in the table. `npm test` (911 tests) and `npm run lint` clean; the portal script parses. **Confirmed in the browser by Ash on 2026-10-23: Settings, Windows event filter opens, Load the suggested starting point fills in the policy, and Save stores it** (the check against sample events, reload, remove and the stale-save refusal have not been reported on).
- **Deploy:** a normal deploy (the schema job creates the table). Nothing to re-run on a broker.
- **Not built here:** the agent group receiving the policy (E4 and later; the broker side is E3, below); a rule-by-rule form in the portal; per-tenant rule limits beyond the global caps (200 rules, 50 strip entries).

## E3 as built (2026-10-24)

A broker that opted in to config from ASIX (`bootstrap-broker.sh --accept-config`) now pulls the tenant's Windows filter, checks it and puts it in `/etc/vector/win-filter.vrl`. **Nothing reads that file until a Windows events input exists (E4, the Wazuh manager's files), so today the program is placed and checked, Vector is not restarted and no event is affected.** What E3 settles is the delivery, so E4 only has to add a source and a transform that reads the file.

- **What travels.** The saved policy becomes ONE Vector program (VRL, from `toVrl()`, with a two-line comment header): `src/endpoints/win-filter-broker.js`. The config pull (`GET /v1/ingest/broker-config`) announces only its **SHA-256** as `config.win_filter` (and inside the signed payload, appended after `paused_inputs`). The broker downloads the text from `GET /v1/ingest/broker-config/win-filter` (same key) and refuses it unless it hashes to exactly the announced value. A hash is small enough for the signed payload (the script accepts at most 2000 base64 characters there) and it names the content: a program changed in transit, or served after the policy changed, does not match. **The hash, not the revision, identifies a program**: a tenant that removes its policy and saves a new one starts again at revision 1.
- **Read from a file, not pasted into a config.** The consumer is a transform with `file: /etc/vector/win-filter.vrl` and `drop_on_abort: true`. Vector does not interpolate environment variables inside a file it loads, so a regex ending in `$` or holding `${...}` reaches the program as written (checked with a real Vector).
- **No policy is the program `.`** (keep every event, change nothing), so a transform that reads the file always has something valid. When the policy is removed, ASIX announces the hash of that program to a broker that last reported another one, and the broker takes the filter away the same way it put it in. A broker that never had a program is told nothing, so every existing answer keeps the shape it had.
- **The broker's steps** (`deploy/broker/asix-broker-config.sh`, step 4, stops at the first failure): skip when the file already has the announced hash; skip a hash it rejected before; download (at most 1 MiB); the hash must match (a mismatch changes nothing and is **not** remembered, the next pull asks again); the file is not empty and has no control characters (tab, newline and carriage return are fine; a NUL byte is refused); `vector validate` on a one-transform config that loads the candidate; keep the old file as `win-filter.vrl.before-config`; install the new one (mode 0644). **Only if a Vector config listed in `VECTOR_CONFIG` mentions `win-filter.vrl`:** validate that whole list, restart Vector, wait for health; any failure puts the old file back (or removes the new one when there was none), restarts Vector on it and remembers the rejected hash in `/var/lib/asix-broker/win-filter-rejected`, so it is not retried every 5 minutes until ASIX announces a different program.
- **Report and the Brokers page.** The broker's report adds `win_filter` (the hash of the file it has, computed from the file, `""` = no file) and `rejected_win_filter`; a broker with no file and nothing rejected sends neither. New columns `collectors.config_win_filter` and `config_rejected_win_filter` (schema job, with CHECKs that allow only a lower-case hash). Settings, Brokers has a **Windows filter** column: **Applied rev N**, **Pending rev N**, **Removing...**, **Rejected rev N**, **Not asking** (no report for 15 minutes), **Not reporting** (a policy is set and the broker never reported: no `--accept-config`, or a script older than E3), a dash when there is no policy. Information only: never a problem and never an alert.
- **Signed mode** works as for the other settings: the broker acts on the hash inside the verified payload and ignores the unsigned `config` part, and the downloaded program must match that hash.
- **A policy too big to send is refused when it is saved** (program over 1 MiB, `MAX_PROGRAM_BYTES` in `win-filter.js`). With today's limits (200 rules, 50 strip entries, 300-character regexes, 100 event IDs each) the largest valid policy makes a program of about 0.7 MB, so this cannot trigger yet; a test fails if the limits are raised past it.
- **Checked:** `tests/win-filter-broker.test.js` (36 tests: program and hash, what the pull announces, the report, the signed payload, both routes, the save-time limit, the page state), `tests/broker-win-filter-script.test.js` (33 tests: the REAL script with the REAL Vector 0.59.0 and REAL openssl, only `id`, `systemctl` and `curl` stubbed; seven deliberate breaks of the script each make it fail, and a first run found a real bug, a NUL byte in a program slipped past a `grep` check, now fixed), `tests/portal-broker-win-filter.test.js` (5 tests), and against a real PostgreSQL 16 with the schema applied twice `tests/win-filter-broker-db.test.js` (the real policy and broker routes, hash announced = hash of the program served, tenant separation, key-and-name binding, removal, Brokers list; three deliberate breaks fail it). `tests/win-filter-db.test.js` (E2) and the new one are now in the CI `postgres` job's list (E2's was missing). `npm test` and `npm run lint` clean.
- **Deploy:** a normal deploy (the schema job adds the two columns). **Then each broker must get the new script:** `git pull`, `chmod +x` the scripts, re-run the bootstrap with `--no-install --accept-config` and EVERY flag again (as in `docs/broker-vm.md`, "Updating a broker after an ASIX deploy"). To try it: save a policy (Settings, Windows event filter), wait up to 5 minutes, see **Applied rev 1** on the broker's row and `/etc/vector/win-filter.vrl` on the broker; Remove the policy and see **Removing...** then a dash, and the file now holding `.`.
- **Not tried:** a real broker VM (everything above ran in the sandbox with the real Vector binary), the column in a browser, the new CI line on GitHub, and a transform that really reads the file on a running broker (that is E4).
- **Not built:** the consumer (E4), the agent group receiving the XPath part, a per-broker policy (it is one policy per tenant), an alert for a filter a broker never applies (the `unknown` and `pending` states are shown, as for ports, but raise nothing).
