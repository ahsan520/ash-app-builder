## What was decided (2026-10-23)

1. **Every endpoint runs one agent, and that agent is Wazuh**, installed by an ASIX installer, for both host security (file integrity, configuration and vulnerability checks, active response) and Windows/Linux event collection. A second event-log agent next to it is not wanted: two collectors on one Security channel double the CPU, duplicate events and give two configs to keep in sync.
2. **Wazuh is behind ASIX, not shown as Wazuh.** The agent installs with ASIX names, the Wazuh manager is a backend service, the Wazuh dashboard is not shipped, and the interface is an **Endpoints** section of the ASIX portal. The product name is **ASIX Endpoint Security** (not "EDR": Wazuh has no kernel-level behavioural prevention, and a client or auditor holding us to the word "EDR" would be a problem; revisit the name only if Sysmon plus active-response playbooks close that gap).
3. **Branded names plus an honest notices page.** Branded service, display and installer names are fine. Hiding Wazuh entirely is not: Wazuh is GPLv2, its copyright and licence notices must stay, customer security reviews and SBOM requests will find the processes anyway, and a modified agent we hand to a client carries a source offer. So the installer and the portal carry a **Third-party notices** page that lists Wazuh and its licence. No Wazuh name or logo is used as ASIX branding, and ASIX never says the code is its own. **Have a lawyer read this before the first client installer ships**; this page is not legal advice.
4. **One Windows filter policy in ASIX, enforced in two places.** Splunk-UF-style allow/deny by event ID (and channel), with an optional regex on a field or on the rendered message, plus removal of the long explanatory text many Windows events end with. The Wazuh agent can filter by event ID (an XPath query in the agent group's `agent.conf`) but has no regex, and its alerts carry the rendered message; so the broker (Vector) always enforces the full policy, and the agent group gets whatever part of it XPath can express, as an optimisation only. The same policy can later compile to a Fluent Bit configuration if an ASIX forwarder is ever needed.
5. **The wall of text is not in the event.** Windows adds it when it renders the message from the provider's message file; the structured EventData is the useful part. The policy therefore offers "remove the rendered message" as well as a regex strip.

## Open decisions (ask before building the tasks that need them)

- **Tenant isolation and manager placement (decided 2026-10-23, from client sizes: most clients 1,000 to 3,000 endpoints, the largest about 10,000).** Wazuh has no native multi-tenancy, and at these sizes a shared manager is not worth its isolation risk. So:
  - **Default: one dedicated single-node manager per tenant** (1,000 to 3,000 endpoints), run centrally (a k3s pod with its own volume, or a VM if the ASIX box lacks the capacity), each reachable on its own address or port. Agents are enrolled with that tenant's registration password and group.
  - **Largest tenants (about 10,000 endpoints): a dedicated Wazuh cluster** (one master and several workers behind a load balancer that agents connect to), on its own VMs, in the ASIX environment or at the client site if the client wants data local or has unreliable links.
  - **Small clients (decided 2026-10-23): their agents connect to a Wazuh manager running on the client's own broker VM** (the "site manager" variant), not to a central one: a small client already has a broker, and nothing has to be exposed centrally. A Wazuh agent never talks to Vector directly; it always talks to a Wazuh manager, and the broker's Vector then reads that manager's `alerts.json` / `archives.json` like any other file input. A manager for a few hundred endpoints should be light enough to share the broker VM (verify on the pinned version and add its needs to the broker VM sizing). A shared central manager with one agent group per tenant stays an option for tiny clients only, later, if ever.
  - **A manager beside the broker is therefore the small-client design, and also the choice for any larger client that needs local collection** (long WAN outages, data residency; the Wazuh agent's event buffer is small by default, verify on the pinned version, so a long outage loses events). The cost is one more service to patch and keep in version step with the agents inside the client's network. Do not stretch one Wazuh cluster across WANs; use independent per-site managers that ASIX manages through the API.
  - **Capacity is the real constraint:** managers need their own cores, memory and fast disk (archives of all events from thousands of endpoints are written to `archives.json` for Vector to read). Size from Wazuh's sizing guidance for the pinned version and from measured event rates; the filter policy (E1) is what keeps these volumes down. The ASIX control plane stays small and the managers move to their own nodes.
  - **The installer takes one parameter, the manager address**, so the tier only decides what it points to: the broker VM (small), a dedicated central manager (mid), or the cluster's load balancer (largest). Moving a client between tiers changes that setting, not the design.
  - **Build order is open: which variant first, the site manager on the broker VM (small clients) or the dedicated central manager (mid clients)?** Both share the same API proxy, alert ingest and parsing pack; they differ in deployment (a broker VM installer step versus a Kubernetes template with address or port allocation). The cluster variant for the largest clients comes after both.
- **Pinned Wazuh version** and the upgrade routine (the manager must be at least as new as its agents).
- **Whether Wazuh keeps its own Windows event rules.** If it does, give it a narrow set (high-value Security IDs and Sysmon) and keep those out of anything else collecting the same events, with ownership per channel and event ID so nothing arrives twice. If ASIX detection owns Windows events, Wazuh's Windows event rules stay quiet; its file integrity, vulnerability and configuration checks are unaffected.

## Architecture

- **Endpoint installer** (E5): the portal generates, per tenant, a Windows script (silent install of a pinned agent package, enrolment with a per-tenant registration password, agent group, branded service names, the filter policy) and a Linux shell script (deb/rpm). Same pattern as the broker installers and keys.
- **Manager** (E4): a backend service; its API is reached only through an ASIX proxy that adds the tenant filter. Alerts and archives go through Vector into the event store as today, with a Wazuh JSON parsing pack mapping `data.win.system` / `data.win.eventdata` into the ASIX fields.
- **Portal** (E6): an Endpoints section (agents with status, version, last seen and group; alerts; file integrity; vulnerabilities; configuration checks; the filter policy; third-party notices).
- **Filter policy** (E1 to E3): E1 is the pure module (rules, validation, evaluation, Vector VRL and Wazuh XPath output). E2 stores it and adds the routes and the portal page. E3 makes a broker apply it (a new kind of broker config next to the syslog port and the pause list: pulled with the broker's own key, validated, applied, health-checked, with a way back).

## E1 as built (2026-10-23)

`src/endpoints/win-filter.js` is a pure module (no I/O, nothing wired into the API or portal yet):

- **Policy shape:** `{ version: 1, default: "keep"|"drop", channels: { <name>: { default } }, rules: [ { id, action: "keep"|"drop", channel?, event_ids?: [4656, "4700-4710"], match?: { field?: "message"|<EventData name>, regex }, note? } ], strip_message: bool, message_strip: [ { channel?, event_ids?, regex } ] }`. Rules are checked in order and the first match wins (so a narrow keep rule placed before a broader drop rule works); no match falls back to the channel default, then the policy default. Channel and field names ignore case. A rule with a regex and no field looks at the rendered message.
- **`validate(policy)`** returns `{ ok, errors, policy }` with the normalised copy (IDs as `[lo, hi]`); limits: 200 rules, 50 strip entries, 300-character regexes, event IDs 0 to 65535.
- **Regex subset:** only syntax that Rust (Vector) and JavaScript read the same way. Rejected, with a message: lookaround, back-references, named groups, inline flags (only `(?: )` groups), `\p \P \k \c \A \z \Z \G`, empty classes `[]` / `[^]`, a `[` or `&& ~~ --` inside a class, a `{` that is not a quantifier, a single quote (write `\x27`) and control characters. Two differences remain and are not detectable: `.` matches `\r` in Rust but not in JavaScript, and `\d \w \s` are Unicode in Rust but ASCII in JavaScript. Use `[^\n]` and explicit classes where it matters. Vector is authoritative; `evaluate()` is for previews and tests.
- **`evaluate(policy, event)`** is the reference behaviour; **`toVrl()` / `toVectorTransform()`** generate a Vector `remap` transform (`drop_on_abort = true`) that must agree with it. The default field paths are a Wazuh Windows event (`data.win.system.channel`, `.eventID`, `.message`, `data.win.eventdata.<name>` with the first letter of each EventData name lower-cased); `paths` changes them. Only the variables a policy uses are defined, so Vector prints no warning.
- **`toXPath(policy, channel)` / `toAgentConf(policy, channels)`** give the Wazuh agent group's `<localfile>` blocks. Only a channel whose rules are all event-ID rules with one action, opposite to the channel's default, gets a `<query>` (an exclusion list or an inclusion list); everything else returns the reason and stays at the broker. The broker enforces the whole policy anyway.
- **`presetNoisySecurity()`** is a suggested starting point only (drop Security 4656, 4658, 4690, 5145, 5156, 5158 and strip the message); it is never applied by itself.
- **Checked:** `tests/win-filter.test.js` (17 tests): validation, the reference evaluation, the XPath and `agent.conf` output, and, with a real Vector binary (`VECTOR_BIN`, or `vector` on PATH; run with Vector 0.59.0), `vector validate` and `vector test` on 14 events, including event IDs as text as Wazuh writes them, show the generated transform keeps, drops and strips exactly what `evaluate()` says, with no VRL warnings; six deliberate breaks each make it fail. Without Vector those tests are skipped. **Not checked: the XPath query length limit Wazuh accepts (1024 characters is a cautious guess to verify on the pinned Wazuh version), that a Wazuh agent accepts the generated `<query>` on a real Windows machine, the Wazuh archive field names on the pinned version.** CI has no Vector, so those Vector tests are not part of CI today.
- **Not built (E2, E3):** storing the policy per tenant, routes, permission, the portal page, and the broker pulling and applying it (a broker script change).

## E2 as built (2026-10-23)

The policy is saved per tenant and edited in the portal; **nothing is sent to a broker or an agent yet (that is E3)**.

- **Table `win_filter_policy`** (in `k8s/12-schema-init.yaml`, created by the normal schema job, idempotent): one row per tenant with the policy as JSONB, a `revision` that goes up by one on every save, `updated_at`, `updated_by`; row security by tenant like the other settings tables. No row means no policy: every event is kept, as before.
- **Routes** (`src/gateway/routes/win-filter.js`, registered in `src/gateway/index.js`; store and request rules in `src/endpoints/win-filter-store.js`): `GET /v1/endpoints/win-filter` (the saved policy, revision, the suggested starting point and the limits; a missing table answers with `available: false` instead of failing), `PUT /v1/endpoints/win-filter` with `{ policy, if_revision? }` or `{ clear: true }`, and `POST /v1/endpoints/win-filter/preview` with `{ policy, events? }` (checks a policy against up to 50 sample events and returns the Vector transform, the Wazuh agent group blocks and per-channel XPath or the reason there is none; touches no database).

- **Portal:** Settings, Data collection, **Windows event filter** (tied to the ingestion module): a JSON editor for the policy, **Check with the sample events** (shows what each sample would do, the agent blocks and the Vector transform), **Save**, **Load the suggested starting point** (the noisy Security IDs preset, never applied by itself) and **Remove the policy**. ## E3 as built (2026-10-24)

A broker that opted in to config from ASIX (`bootstrap-broker.sh --accept-config`) now pulls the tenant's Windows filter, checks it and puts it in `/etc/vector/win-filter.vrl`. **Nothing reads that file until a Windows events input exists (E4, the Wazuh manager's files), so today the program is placed and checked, Vector is not restarted and no event is affected.** What E3 settles is the delivery, so E4 only has to add a source and a transform that reads the file.

- **What travels.** The saved policy becomes ONE Vector program (VRL, from `toVrl()`, with a two-line comment header): `src/endpoints/win-filter-broker.js`. The config pull (`GET /v1/ingest/broker-config`) announces only its **SHA-256** as `config.win_filter` (and inside the signed payload, appended after `paused_inputs`). The broker downloads the text from `GET /v1/ingest/broker-config/win-filter` (same key) and refuses it unless it hashes to exactly the announced value. A hash is small enough for the signed payload (the script accepts at most 2000 base64 characters there) and it names the content: a program changed in transit, or served after the policy changed, does not match. **The hash, not the revision, identifies a program**: a tenant that removes its policy and saves a new one starts again at revision 1.
- **Read from a file, not pasted into a config.** The consumer is a transform with `file: /etc/vector/win-filter.vrl` and `drop_on_abort: true`. Vector does not interpolate environment variables inside a file it loads, so a regex ending in `$` or holding `${...}` reaches the program as written (checked with a real Vector).
- **No policy is the program `.`** (keep every event, change nothing), so a transform that reads the file always has something valid. When the policy is removed, ASIX announces the hash of that program to a broker that last reported another one, and the broker takes the filter away the same way it put it in. A broker that never had a program is told nothing, so every existing answer keeps the shape it had.
- **The broker's steps** (`deploy/broker/asix-broker-config.sh`, step 4, stops at the first failure): skip when the file already has the announced hash; skip a hash it rejected before; download (at most 1 MiB); the hash must match (a mismatch changes nothing and is **not** remembered, the next pull asks again); the file is not empty and has no control characters (tab, newline and carriage return are fine; a NUL byte is refused); `vector validate` on a one-transform config that loads the candidate; keep the old file as `win-filter.vrl.before-config`; install the new one (mode 0644). **Only if a Vector config listed in `VECTOR_CONFIG` mentions `win-filter.vrl`:** validate that whole list, restart Vector, wait for health; any failure puts the old file back (or removes the new one when there was none), restarts Vector on it and remembers the rejected hash in `/var/lib/asix-broker/win-filter-rejected`, so it is not retried every 5 minutes until ASIX announces a different program.
- **Report and the Brokers page.** The broker's report adds `win_filter` (the hash of the file it has, computed from the file, `""` = no file) and `rejected_win_filter`; a broker with no file and nothing rejected sends neither. New columns `collectors.config_win_filter` and `config_rejected_win_filter` (schema job, with CHECKs that allow only a lower-case hash). Settings, Brokers has a **Windows filter** column: **Applied rev N**, **Pending rev N**, **Removing...**, **Rejected rev N**, **Not asking** (no report for 15 minutes), **Not reporting** (a policy is set and the broker never reported: no `--accept-config`, or a script older than E3), a dash when there is no policy. Information only: never a problem and never an alert.
- **Signed mode** works as for the other settings: the broker acts on the hash inside the verified payload and ignores the unsigned `config` part, and the downloaded program must match that hash.
- **A policy too big to send is refused when it is saved** (program over 1 MiB, `MAX_PROGRAM_BYTES` in `win-filter.js`). With today's limits (200 rules, 50 strip entries, 300-character regexes, 100 event IDs each) the largest valid policy makes a program of about 0.7 MB, so this cannot trigger yet; a test fails if the limits are raised past it.

## E4a as built (2026-10-24)

A broker set up with `--wazuh` now reads Windows events from a Wazuh manager's archive file, passes each one through the tenant's Windows event filter (E3), and sends what is left to ASIX with source type `windows-event`, where ASIX's own Windows parsing rules read it. **There is no Wazuh manager in this build** (that is E4b): the input waits for the file. What E4a settles is everything after the file, so the manager work only has to produce it.

- **Standard path, as agreed.** `/var/ossec/logs/archives/archives.json`; `--wazuh-archives PATH` (written as `ASIX_WAZUH_ARCHIVES`) changes it. The manager writes this file only with `<logall_json>yes</logall_json>` in its `ossec.conf` (it logs every event, so watch the disk; E4b sets it and the rotation). Read from the END on the first start (no backlog), a file that appears later (the daily rotation) from its start; lines up to 256 KB so a long Windows message is not cut in the middle of the JSON.
- **The chain** (`deploy/broker/vector-wazuh.yaml`, three transforms): `wazuh_parse` (JSON, Windows event channel events only: Linux agent lines, the manager's own lines and anything that is not JSON are skipped) -> `win_filter` (the program in `/etc/vector/win-filter.vrl`, read from a FILE so a regex with `$` or a dollar-brace reaches it as written; a dropped event is gone here, on the broker, before it costs bandwidth) -> `wazuh_to_event` (the ASIX event). The sink sends a **JSON array** with the key, `X-ASIX-Collector` (the broker name) and `X-ASIX-Source-Type: windows-event` in headers, on a disk buffer, like the other inputs.
- **The event ASIX gets** is the shape its Windows parsing already reads: `message` = `[Channel] Provider id=N <the message text on one line>` (empty text when the policy strips messages), `time` = the event's own time (`systemTime`, else the manager's), `host` = the Windows computer name (else the agent name), and `fields` = the event's named data with the first letter upper-cased again (Wazuh writes `targetUserName`, Windows and the ASIX rules say `TargetUserName`) plus `asix_via=wazuh`, `agent_name`, `agent_id`, `agent_ip`, `win_event_id`, `win_record_id`. So the Sysmon rules and every message-based Windows rule work on Wazuh events with no change.
- **The ingest lane takes a JSON array** (`POST /v1/ingest/http`, `src/ingest/http-ingest.js`): each element `{message | raw, time?, host?, fields?}`, with the collector, platform and source type from the same headers as text lines (source type `json` when none). Elements that are not objects or have no message are skipped; the older text and `{collector, source_type, events}` bodies are unchanged. A Vector `http` sink with `codec: json` sends exactly this, so no new endpoint was needed.
- **New parsing rules for Wazuh events** (`src/ingestion/default-parsing-rules.js`, before the message-based Windows section; they apply only when `asix_via = "wazuh"`): `wazuh_windows_logon` (4624, 4625, with the failure reason spelled out from Windows' `%%23xx` codes), `wazuh_windows_process` (4688), `wazuh_windows_scheduled_task` (4698 to 4702), `wazuh_windows_account` (4720 to 4740), `wazuh_windows_group` (4728 to 4757), `wazuh_windows_service` (7045, 4697). **Why they exist:** the suggested starting point of the policy strips every message, and the old rules read the message text, so without them a stripped 4625 would lose its user and address. They give the same fields as the message rules (a test compares them event by event, with and without text); the one improvement is `group_name`, which the old message rule never found for the current Windows wording. Every other Wazuh event falls through to the message rules (a stripped 1102 is still categorised as a cleared log, but has no user: its data is not in `eventdata`), and Sysmon already read named fields.
- **Same machinery as the other inputs.** `--wazuh` installs `vector-wazuh.yaml`, puts the keep-everything filter in `/etc/vector/win-filter.vrl` when there is none (Vector will not start without the file; never over a policy already there; byte for byte the program ASIX announces for "no policy", so nothing is re-downloaded), adds the vector user to the `wazuh` group when there is one, writes `ASIX_WAZUH_ARCHIVES` and adds the file to `VECTOR_CONFIG`; a re-run without `--wazuh` removes the config and leaves the filter. The heartbeat reports the input (**Windows events** on the Brokers page, Inputs column), `upgrade-broker.sh` and `asix-broker-config.sh` validate it with the others, and it can be **paused** like Log files, HTTP and Journal (Paused column; Vector keeps its place in the file, so resuming continues where it stopped). **From now on `asix-broker-config.sh` finds a reader of `win-filter.vrl`**: a changed policy is validated against the whole config, Vector restarted, health checked and the old program put back on a failure, exactly as E3 described.
- **Checked:** `tests/broker-wazuh.test.js` (34 tests: the files agree, the bootstrap block run in bash, every rule against ten sample events, the lane's array body with the DB and rule engine stood in, and the REAL Vector 0.59.0 reading a real archive file with the REAL filter programs: keep everything, the suggested starting point, and a policy with `$` and a dollar-brace in its regexes); `tests/broker-wazuh-db.test.js` (real Vector -> the real ingest route -> real PostgreSQL 16: nine events stored and parsed, the dropped one never arrives; skips without Vector, so the CI job lists it but cannot run it); seven deliberate breaks of the config, rules and lane each fail the tests. `npm test` and `npm run lint` clean.
- **Not tried, and the one real risk:** the sample events are hand-made from Wazuh's documented eventchannel format (`data.win.system` and `data.win.eventdata` with the first letter lower-cased), **not captured from a live manager**. If a real Wazuh names a field differently, that rule's field comes out empty and the event still arrives with its channel, provider, id and message (never lost). E4b is where one real event of each kind is checked; the sample file is `tests/fixtures/wazuh-windows.js`. Not run on a real broker VM, and the Brokers page changes not seen in a browser.
- **Deploy:** a normal deploy (the parsing rules and the ingest lane are in the API image; no schema change). **Nothing changes on a broker until you turn it on:** `git pull`, `chmod +x` the scripts, and re-run the bootstrap with `--no-install` and EVERY flag again plus `--wazuh` (and `--accept-config` if the broker takes config). Without a manager there is no file yet, which is fine: the input waits. To try it without a manager, on the broker: `sudo install -d -o root -g vector -m 750 /var/ossec/logs/archives` (or use `--wazuh-archives` with a folder of your own), append one line from `tests/fixtures/wazuh-windows.js` (print it on a machine that has the repo and Node, not necessarily the broker: `node -e "const F=require('./tests/fixtures/wazuh-windows');console.log(F.line(F.events.failedLogon))"`) to the file, and look under Events for source type `windows-event`.
- **Not built:** the manager and its install (E4b), the central manager and the API proxy (E4c), Linux and macOS agent events and Wazuh alerts, the agent group receiving the XPath part of the policy (a later task), and field-based rules for UserData events (1102, 104) and the less common Security events.

## E4b as built (2026-10-24)

`scripts/deploy/install-wazuh-manager.sh` installs a Wazuh **manager** (only the manager: no indexer, no dashboard, ASIX stores and searches the events) on the broker VM and sets it up so that Windows agents report to it, it writes every event to `/var/ossec/logs/archives/archives.json`, and the broker's Vector (E4a) reads that file through the tenant's filter. `bootstrap-broker.sh --wazuh-manager [--wazuh-keep-days N]` runs it for you (and implies `--wazuh`).

- **Version: 4.14.9-1**, pinned in one place (`WAZUH_VERSION` in the script). It is the latest stable release in Wazuh's own release index (14 October 2026; a 4.14.10 release candidate exists and is not used). The package is **put on hold** after the install, so `apt upgrade` never changes the manager; an upgrade is deliberate (`--version NEW --upgrade`, after backing up `/var/ossec/etc`). **An agent must be the same version or older than its manager**: install agents of 4.14.9 or older.
- **What it does, in order, each step safe to repeat:** (1) checks: root, apt and systemd, CPUs, memory, free disk, ports 1514, 1515 and 55000 not in use, the Wazuh repository reachable. `--check` does only this and changes nothing. (2) adds the Wazuh apt repository (key in `/usr/share/keyrings/wazuh.gpg`; **the key's fingerprint is printed so you can compare it with Wazuh's documentation, and `--key-fingerprint` makes it a requirement**), installs `wazuh-manager=4.14.9-1`, holds it. (3) `ossec.conf`: the original is kept once as `ossec.conf.before-asix`, `deploy/wazuh/ossec-edit.py` makes **four** changes (`logall_json` on, so archives.json is written; `use_password` on, so an agent needs the enrolment password; vulnerability detection and indexer off, they need an indexer a broker VM does not run), then the manager's own config test (`wazuh-analysisd -t`) runs; **if it fails the previous file is put back and nothing is started**. (4) `/var/ossec/etc/authd.pass`: a random enrolment password, created once, never overwritten, readable by root and the `wazuh` group, never printed. (5) a daily clean-up (`asix-wazuh-prune.timer`, 03:30): the manager rotates archives.json and alerts.json every day and never deletes anything, so rotated files older than `--keep-days` (default 3; ASIX has the events) are removed, and **if the disk is 90% full it keeps one day only** and says so in `journalctl -u asix-wazuh-prune`. The live files the broker is reading are never touched. (6) starts the manager and waits for it to listen on 1514 and 1515.
- **Ports:** 1514/tcp agents, 1515/tcp enrolment (and 55000 the manager's API, 1516 its cluster port; neither is opened to anyone by this build). The script does not open the firewall. **A syslog port of 1514, 1515, 1516 or 55000 can no longer be used on a broker that has the manager:** `bootstrap-broker.sh` refuses `--port`, `--tls-port` and `--http-port` with those numbers when `--wazuh-manager` is given, and `asix-broker-config.sh` ignores a syslog or TLS port from ASIX that clashes with a manager installed on that broker (it only notices a manager that is there, so other brokers can still use 1514).
- **Sizing (my estimate, not a measurement; look again after the first week).** The manager's daemons (analysis, remote, database, API) take about 2 to 3 GB at 50 agents; Vector with its disk buffer about 0.5 GB; the operating system 1 GB. Disk is archives.json at about 2 KB per event: events per second x 0.17 = GB per day for the live day (200 events/s is about 35 GB), rotated files compress about ten to one and are kept `--keep-days` days. Windows servers vary a lot (a busy domain controller can send more than 200 events/s; the filter only drops events on the broker AFTER the manager has written them, so it does not reduce this disk use; dropping at the agent is the later XPath task).

  | Broker VM | CPUs | Memory | Disk (SSD) | For |
  | --- | --- | --- | --- | --- |
  | minimum the installer accepts | 2 | 3.5 GB | 20 GB free | a lab, a few agents (it warns below 8 GB) |
  | **recommended** | **4** | **8 GB** | **100 GB** | **a small client: up to about 50 agents and 200 events/s sustained** |
  | larger | 8 | 16 GB | 250 GB | up to about 150 agents, or busier servers; beyond that the central manager (E4c) |
- **Enrolling a Windows machine** (the installer prints the exact lines at the end): download `wazuh-agent-4.14.9-1.msi` from `packages.wazuh.com/4.x/windows/`, then in an elevated PowerShell `msiexec.exe /i wazuh-agent.msi /q WAZUH_MANAGER='BROKER-ADDRESS' WAZUH_REGISTRATION_PASSWORD='<the line in /var/ossec/etc/authd.pass>' WAZUH_AGENT_NAME='PC-NAME'` and `NET START WazuhSvc`. The agent's default configuration reads the Application, Security and System logs and Sysmon when it is there; which channels and which event IDs it reads is the later agent-group task (the XPath part of the policy). The installer generator (E5) will do this per tenant.
- **Checked** (`tests/broker-wazuh-manager.test.js`, 39 tests): the ossec.conf editor against a default-shaped config (exactly four lines change, nothing else moves, a second run changes nothing, commented-out blocks are never edited, a missing required block stops it without writing); the clean-up script on a made-up tree (old rotated files go, live files and young ones stay, empty folders go, the disk guard); the installer with stand-ins for apt, dpkg, curl, gpg, systemctl, ss, df and nproc in a made-up /var/ossec (checks, a full install, a re-run, a different installed version, a failing config test puts the file back, a manager that does not start, the fingerprint rule); the bootstrap's own checks; the port clash. - **NOT tested, and the risks:** the real `wazuh-manager` package, the real manager starting, a real agent enrolling, and the real default `ossec.conf` (the sample is written from the documented shape). The installer is built so a surprise is safe rather than silent: the config is checked by the manager's own `wazuh-analysisd -t` before anything starts and restored on failure, the editor refuses to write when it cannot find the two required blocks, and `--check` shows what it would be up against. **If the first run stops, send me the last 30 lines of the output and `tail -n 50 /var/ossec/logs/ossec.log`.** After the first Windows agent has sent events, one real line of each kind from archives.json (`sudo head -c 3000 /var/ossec/logs/archives/archives.json` for a start) is what the sample file `tests/fixtures/wazuh-windows.js` and the E4a parsing rules need to be checked against.

## E4c as built (2026-10-25)

Mid-size clients (1,000 to 3,000 endpoints) get a **dedicated central manager**, and ASIX can now **read its agents through a tenant-bound, read-only proxy**. No Windows machine exists yet, so nothing below has seen a real agent, and **no real Wazuh manager was available either: everything was tested against a stand-in of the Wazuh API written from its documented 4.x shape.**

**Decisions taken here (change them if you disagree).**
- **The central manager is a VM, not a Kubernetes pod.** The design allowed both. A manager for thousands of endpoints needs several cores, 16 GB or more and fast disk, which a lab k3s box does not have; the official container image bundles a log shipper that needs an indexer ASIX does not run, and I could not verify how to switch it off or how it takes its configuration; and a VM reuses the E4b installer and the E4a Vector input unchanged. So **a central manager is a broker VM that ASIX staff run**: `bootstrap-broker.sh --wazuh-manager [--accept-config]` with that tenant's broker key (events flow exactly as in E4a/E4b), then `wazuh-api-setup.sh` (below). A pod template can follow if a capacity reason appears.
- **No route registers a manager.** ASIX's API connects to the stored address with a password; if a tenant user could choose that address the API could be aimed at things it can reach and they cannot. An operator registers with `src/endpoints/wazuh-manager-cli.js` (inside the API image, run with `kubectl exec`); the routes only read.
- **"Tenant filter" = a tenant can only reach its own manager, and cannot steer the call.** One manager per tenant, so there is no query condition to forget: the row is read under row security; the method is always GET; the path is one of four fixed ones; the query string is rebuilt from six validated parameters (`limit`, `offset`, `status`, `search`, `sort`, `os_platform`) and anything else is a 400; the answer is rebuilt from an allow-list of agent fields (so `configSum`, `mergedSum`, `uname` and whatever a later Wazuh adds are never passed on). A shared manager with one agent group per tenant would need a forced `group` here and is not built.
- **Permissions: `capacity:read`**, as for the Windows filter page (no role change). Agent names and addresses are a bit more sensitive than that page's contents; give them their own permission later if wanted.
- **Split again:** Wazuh alert ingest is now **E4d** (see "Not built").

**What was built.**
- **Table `wazuh_managers`** (schema job, idempotent; row security by tenant): API address (`https://host:port` only, enforced by a CHECK), API user, password sealed with `NOTIFY_ENCRYPTION_KEY` (the notification channels' key), the manager API's own certificate, its SHA-256, a label.
- **Proxy client** `src/endpoints/wazuh-api.js`: signs in with `POST /security/user/authenticate?raw=true`, keeps the token per tenant until 30 s before it expires and replaces it once on a 401; **trusts only the stored certificate** (Wazuh's is self-signed; pinning the exact certificate is stricter than a public CA check, and the handshake fails before the password is sent to anything else); no redirects; 8 s timeout (`ASIX_WAZUH_API_TIMEOUT_MS`); 2 MB cap; at most 4 calls at once per tenant (the 5th is refused with 503); loopback, link-local (cloud metadata) and reserved addresses refused at registration AND at connect time (private addresses are fine: a manager is a machine in your network). `ASIX_WAZUH_ALLOW_LOOPBACK=true` lifts the loopback rule for a lab where the manager is on the API's own machine.
- **Routes** (`src/gateway/routes/wazuh-manager.js`): `GET /v1/endpoints/manager` (registered? host, port, user, certificate fingerprint, and live status with the Wazuh version; an unreachable manager is a state in a 200, not an error), `GET /v1/endpoints/agents/summary`, `GET /v1/endpoints/agents`, `GET /v1/endpoints/agents/:id`. Errors: 404 `WAZUH_NO_MANAGER`, 400 for a bad query or id, 502/504 `WAZUH_AUTH_FAILED | TLS | UNREACHABLE | TIMEOUT | BAD_RESPONSE`, 503 `WAZUH_NO_KEY` or `WAZUH_NOT_READY`, 500 `WAZUH_SECRET` (the key changed: register again).
- **Operator tool** `src/endpoints/wazuh-manager-cli.js` (`register | show | check | remove --tenant NAME-or-ID`): `register` reads the JSON from standard input (never from arguments), **signs in to the manager first and saves only if that works** (`--no-check` to save anyway), and a second `register` replaces the first.
- **`scripts/deploy/wazuh-api-setup.sh`, run on the manager VM** after the installer: (1) **replaces the default passwords of the API users `wazuh` and `wazuh-wui`** (a new manager has well-known defaults with full rights; E4b started the API on port 55000 without changing them, so until this runs anything that can reach that port could sign in; the installer does not open the firewall, but run this soon after installing); (2) creates the read-only API user `asix-readonly` with the `readonly` role; (3) tries what ASIX will do as that user (read the manager info, list agents) and stops if it cannot; (4) writes `asix-wazuh-registration.json` (address, user, password, certificate), root-only. `--check` only looks. Passwords are random, saved root-only in `/var/ossec/etc/asix-api-*.pass` before they are used, never printed and never on a command line; the API is reached with the certificate pinned (`curl --pinnedpubkey`). Safe to run again.
- **Checked.** `tests/wazuh-api.test.js` (21 tests, real HTTPS against a stand-in): the parameters, what is sent and passed on, token reuse and renewal, a wrong certificate refused before anything is sent, redirect, huge and slow answers, forbidden addresses, the call limit; seven deliberate breaks each fail it. `tests/wazuh-manager-store.test.js` (7). `tests/wazuh-manager-db.test.js` (real PostgreSQL 16, schema applied twice; `ASIX_TEST_DB=1`): the real routes, the real CLI and two stand-in managers: each tenant reaches its own manager and a tenant with none reaches nothing, bad requests send nothing, **no other method on these paths does anything**, the password is not in the row, row security as a non-superuser role, the key changed or missing; breaking row security or adding a write route each fails it. `tests/wazuh-api-setup-script.test.js` (14 tests, the real script with the real curl, openssl and python3 against a stand-in in its "fresh manager" mode): passwords changed, role given, a registration file the proxy accepts and signs in with, idempotent re-run, `--rotate`, a wrong certificate refused before any request, a refused change leaves the default alone, no secret in output or arguments; four deliberate breaks fail it. The new DB test is in the CI `postgres` job's list. `npm test` and `npm run lint` clean.
- **NOT checked, and the risks, in the order they are likely to bite:** (1) **the real Wazuh API**: the endpoints, field names and answer shapes (`/security/users`, `/security/roles`, `role_ids`, `/agents/summary/status` with a `connection` block, the raw token answer) are from the documented 4.x API and may differ on 4.14.9; the script and the proxy stop with a message rather than guess, and the stand-in's shapes are in `tests/fixtures/fake-wazuh-api.js` to compare against a real answer. (2) **That the built-in `readonly` role may read agents and the manager info** (the script's last step tells you). (3) **The default location of the API certificate** (`/var/ossec/api/configuration/security/server.crt`; the script falls back to reading it from the running API). (4) A real Windows agent connecting to a central manager over a WAN. (5) The sizes below.
- **Sizing for a central manager (my estimate, not a measurement; replace it with real numbers).** Same arithmetic as E4b: disk about 2 KB per event, `events per second x 0.17` GB per day for the live day. For 1,000 to 3,000 endpoints plan **8 CPUs, 16 GB, 250 GB SSD to start** and measure; beyond about 3,000 busy endpoints, or if the manager's analysis queue backs up, move that tenant to a cluster (not built). `install-wazuh-manager.sh` warns below 8 GB, so for a central VM read its `--check` with these numbers in mind.
- **Deploy and first run, in this order.** (1) Normal deploy (the schema job creates `wazuh_managers`; the API image has the proxy and the tool). (2) Create the manager VM (sizes above), then follow `docs/broker-vm.md` with that tenant's broker key and `--wazuh-manager`. (3) On that VM: `sudo ./scripts/deploy/wazuh-api-setup.sh --check`, then `sudo ./scripts/deploy/wazuh-api-setup.sh --address <the VM address ASIX reaches> --label "<client> central manager"`. (4) Let only the ASIX node reach port 55000 on the VM; agents need 1514 and 1515 as in E4b. (5) Copy `asix-wazuh-registration.json` to the machine with kubectl, then `kubectl -n asix-platform exec -i deploy/asix-api -- node src/endpoints/wazuh-manager-cli.js register --tenant "NAME" < asix-wazuh-registration.json` and delete the copy. (6) As a user of that tenant, `GET /v1/endpoints/manager` shows the version; `GET /v1/endpoints/agents` lists agents (none until a machine is enrolled). If the setup script stops, send me its output (it never prints a password).
- **Not built:** (Wazuh alerts into ASIX were built as E4d, below; ASIX alerts raised from them as E4e), a manager as a Kubernetes pod, a cluster, a shared manager with one agent group per tenant, any write through the proxy (restart or delete an agent, change a group), an alert when a registered manager stops answering, and moving a client between manager tiers.

## E4d as built (2026-10-25)

**Scope.** Only the alerts part of the old E4d. A manager as a pod stays out (decided in E4c: a VM) and a cluster is for later.

- **Input.** `deploy/broker/vector-wazuhalerts.yaml`, installed by `bootstrap-broker.sh --wazuh-alerts` (`--wazuh-alerts-file`, `--wazuh-alerts-min-level`). Reads `/var/ossec/logs/alerts/alerts.json` from its end, skips lines that are not JSON, have no rule or no rule id, or are below the minimum level, and sends a JSON array per batch to the HTTP lane with source type `endpoint-alert`, through its own sink and disk buffer. - **Parts:** `src/endpoints/templates/agent-install-windows.ps1` (the script, plain ASCII so Windows PowerShell 5.1 reads it correctly), `renderWindows` in `src/endpoints/agent-installer.js` (same fields and the same strict validation as Linux: address, group, agent version), the route **`GET /v1/endpoints/installer/windows?group=NAME`** (`capacity:read`; registered next to the Linux route in `src/gateway/routes/wazuh-manager.js`, one handler for both; address from the registry, never from the request; same version rule and the same fallback to `4.14.9-1`) and a **System** choice (Linux or Windows) in the **Add a machine** tab. Exit codes as on Linux: 0 done, 1 a problem (nothing changed, or enrolment failed), 2 usage, 3 installed and enrolled but not connected.
- **What it does, in order, each step safe to repeat:** (1) checks: administrator, PowerShell 5 or newer, the installed agent version (from the Uninstall registry keys), the manager answers on 1514 and 1515, the package can be fetched, a password is available. (2) downloads `https://packages.wazuh.com/4.x/windows/wazuh-agent-<version>.msi` to a temporary file, prints its SHA-256, **refuses it unless Windows says its Authenticode signature is valid**, prints who signed it, installs it silently with `WAZUH_MANAGER`, `WAZUH_AGENT_GROUP`, `WAZUH_AGENT_NAME` (exit codes 0 and 3010 accepted), removes the temporary file. (3) if there is no `client.keys` (or `-ReEnroll`): writes the password to `authd.pass` in the agent folder, restricts it to SYSTEM and Administrators with `icacls`, runs `agent-auth.exe -m MANAGER -p 1515 -G GROUP -A NAME`, and removes the file in every case. (4) names the service "ASIX Endpoint Security agent" (the service `WazuhSvc` and the package keep their upstream names), sets it to start automatically, restarts it. (5) waits (60 s, `ASIX_AGENT_WAIT_S`) for a **new** "Connected to the server" line in `ossec.log`; an older line does not count.
- **Decisions that differ from Linux:**
  - **The password is never on the msiexec command line** (it would show in the process list and in the installer's verbose log). The package is installed without `WAZUH_REGISTRATION_PASSWORD` and the script enrols with `agent-auth` through the temporary file. If the package happens to enrol by itself, the script sees a key and does not enrol again.
  - **A password typed in the portal goes into the script as base64 of its UTF-8 bytes** (in the browser only; the request carries the group only), and the script decodes it. PowerShell treats the curly quote characters as quotes too, so quote-escaping a password is not safe; base64 has no characters that can break out of the string. It is not encryption: the script is as secret as the password, and the page says so.
  - **No repository key**: Windows has no package repository here, so the check is the Authenticode signature plus an optional pinned hash (`-MsiSha256`), instead of Linux's key fingerprint.
  - **Extra words on the command line are refused** (exit 2) rather than silently taken as `-Name`.
